# DB-Query-RS Constitution

## Core Principles

### I. Ergonomic Rust Code Style

**Rule**: All backend code MUST follow ergonomic Rust style guidelines to ensure readability and consistency across the codebase.

**Requirements**:
- Prefer idiomatic Rust patterns (Result/Option types, pattern matching, iterators)
- Use meaningful variable and function names that convey intent
- Leverage Rust's type system for compile-time guarantees
- Follow standard Rust formatting (rustfmt) and linting (clippy) rules
- Code must be self-documenting with clear structure and minimal complexity

**Rationale**: Ergonomic Rust code maximizes the language's safety and performance benefits while maintaining developer productivity and code maintainability. Consistency reduces cognitive load when reading and reviewing code.

### II. camelCase Data Format (NON-NEGOTIABLE)

**Rule**: All data generated by the backend MUST use camelCase formatting for field names in API responses, JSON payloads, and database metadata representations.

**Requirements**:
- API response fields: `{ "tableName": "users", "columnCount": 5 }`
- Serialization configured for camelCase (e.g., serde with rename_all)
- Internal Rust structs can use snake_case (following Rust conventions), but serialization outputs camelCase
- Documentation must reflect camelCase in examples and contracts

**Rationale**: Maintains consistency with frontend JavaScript/TypeScript conventions where camelCase is standard, reducing impedance mismatch between backend and frontend. This is non-negotiable to ensure API contract stability.

### III. Open Access - No Authentication

**Rule**: The system MUST NOT implement authentication or authorization mechanisms. Any user can access all features and data.

**Requirements**:
- No user registration, login, or session management
- No API keys, tokens, or credentials required for endpoints
- All database connections and queries are accessible to all users
- CORS configured to allow all origins

**Rationale**: This is a developer tool designed for local or trusted network usage where authentication adds unnecessary complexity. Users are responsible for network-level access control. This simplifies development and deployment while meeting the intended use case.

## Technology Stack

**Required Technologies**:
- **Language**: Rust (using idiomatic Rust practices)
- **Web Framework**: Axum (for HTTP server and routing)
- **Database Library**: SQLx (for database connections and queries)
- **LLM Integration**: openai_api_rust SDK (for natural language to SQL conversion)
- **Metadata Storage**: SQLite (stored in `./db-query/db_query.db`)
- **Target Databases**: PostgreSQL (primary support), extensible to others

**Configuration**:
- OpenAI API key via `OPENAI_API_KEY` environment variable
- CORS enabled for all origins
- SQL query validation with automatic LIMIT 1000 clause if omitted

## Security & Access

**Query Safety**:
- All SQL queries MUST be validated to contain only SELECT statements
- Queries lacking LIMIT clauses MUST automatically have `LIMIT 1000` appended
- SQL syntax validation required before execution
- Malformed queries return descriptive error messages

**Data Exposure**:
- System assumes trusted environment (no authentication)
- Database credentials stored in SQLite are accessible to all users
- Network-level security is the user's responsibility

## Governance

**Amendment Process**:
1. Proposed changes must document rationale and impact
2. Constitution version increments follow semantic versioning:
   - **MAJOR**: Backward-incompatible principle removals or redefinitions
   - **MINOR**: New principles or materially expanded guidance
   - **PATCH**: Clarifications, wording improvements, non-semantic fixes
3. All template files must be reviewed for consistency after amendments
4. Migration plan required for breaking changes

**Compliance**:
- All features and PRs must verify alignment with Core Principles
- Deviations require explicit justification in design documents
- Constitution supersedes other practices in case of conflict
